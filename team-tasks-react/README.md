# Командный трекер задач

Учебное одностраничное приложение (SPA) на React, React Router, Redux Toolkit и RTK Query. Проект реализует практическую часть семинара «SPA, Redux Toolkit и RTK Query» и использует предоставленный локальный API.


## 1. Требования и запуск

Требуется Node.js 22.12 или новее и npm.

### Установка зависимостей

Из корня проекта:

```bash
npm install
```

В каталоге API:

```bash
cd api
npm ci
cd ..
```

При первой установке фронтенда `npm install` создаст `package-lock.json`. Его следует добавить в Git. После сохранения lock-файла для последующих чистых установок используйте `npm ci`.

### Запуск

Откройте два терминала из корня проекта.

**Терминал 1 — локальный API:**

```bash
npm run api
```

Или отдельно:

```bash
cd api
npm start
```

API запускается на `http://127.0.0.1:3001`. При первом запуске создаётся `api/data/db.json` на основе `api/src/seed.json`. Изменения задач сохраняются в JSON-файл и переживают перезапуск API.

**Терминал 2 — React:**

```bash
npm run dev
```

Откройте `http://localhost:5173`.

### Переменные окружения

Скопируйте `.env.example` в `.env`, если нужно изменить адрес API:

```dotenv
VITE_API_URL=http://127.0.0.1:3001
```

После изменения `.env` перезапустите Vite. Для нестандартного адреса фронтенда добавьте его в `CORS_ORIGINS` при запуске API (список origin через запятую). Не задавайте `HOST=0.0.0.0` для обычной учебной работы: сервер по умолчанию доступен только с этого компьютера.

## 2. Функциональные маршруты

| URL | Экран | Проверка |
| --- | --- | --- |
| `/users` | Список участников | Загружается команда из API |
| `/users/:userId` | Профиль участника | Вложенный маршрут, index route |
| `/users/:userId/tasks` | Задачи участника | Список задач без фильтра |
| `/users/:userId/tasks?status=todo` | Задачи с фильтром | Фильтр хранится в URL |
| `/tasks/:taskId` | Просмотр и редактирование задачи | Страница загружается через `lazy` / `Suspense` |
| `/favorites` | Избранные участники | Общий Redux slice и selectors |
| `*` | Страница 404 | Неизвестный URL |

Вложенные маршруты участника используют общий `UserLayout` и `Outlet`. Прямой вход по ссылке поддерживается Vite dev server. При публикации статического SPA на хостинге сервер необходимо настроить так, чтобы неизвестные пути приложения возвращали `index.html`.

Внутренние переходы выполняются через React Router. Фильтр `status` синхронизирован с query string, поэтому Back/Forward восстанавливает соответствующий экран. Некорректное или повторяющееся значение `status` удаляется из URL.

## 3. Модели и API

Модели соответствуют слайду 32 семинара:

```js
User = { id, name, email }
Task = { id, userId, title, status }
status = 'todo' | 'doing' | 'done'
```

Все ID — строки.

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| `GET` | `/users` | Список участников |
| `GET` | `/tasks?userId=1&status=todo` | Фильтрованный список задач; `status` необязателен |
| `GET` | `/tasks/:id` | Одна задача |
| `POST` | `/tasks` | Создание задачи |
| `PATCH` | `/tasks/:id` | Изменение названия и/или статуса |
| `DELETE` | `/tasks/:id` | Удаление задачи |

Начальные данные содержат 4 участника и 8 задач. Ответы API сохраняются в `api/data/db.json`; этот файл намеренно исключён из Git, чтобы локальные изменения не попадали в репозиторий.

## 4. Архитектура и разделение состояния

| Данные / ответственность | Где находятся | Почему |
| --- | --- | --- |
| Участники, статус загрузки, ошибка, `requestId` | `usersSlice` | Общие данные команды нужны на разных страницах |
| Загрузка участников | Собственный `usersMiddleware` и `fetch` | Это обязательная часть практики |
| Избранные ID | `uiSlice` | Согласованное состояние карточек, профиля и счётчика |
| Задачи, статусы запросов и кэш | RTK Query (`tasksApi`) | Серверные данные не дублируются в обычном slice |
| Фильтр задач | URL search params | Состояние восстанавливается по ссылке и истории браузера |
| Значения форм и сообщения формы | Локальный `useState` | Эти данные нужны только конкретному экрану |

### Участники: собственный middleware

1. Компонент отправляет `usersRequested()`.
2. Middleware сначала вызывает `next(action)`, затем проверяет `users.status` и не запускает параллельный запрос, пока предыдущий ещё выполняется.
3. Middleware отправляет `usersLoading`, выполняет `fetch('/users')`, проверяет `response.ok`, разбирает JSON и валидирует структуру массива.
4. При успехе отправляется `usersLoaded`, при ошибке — `usersFailed`.
5. Reducer принимает результат только для актуального `requestId`, поэтому поздний ответ не перезаписывает более новый.
6. У запроса есть тайм-аут 10 секунд; после ошибки доступна кнопка повтора.

`createAsyncThunk` не используется вместо middleware: собственный middleware сохранён, как требует слайд 34.

### Задачи: RTK Query

В `tasksApi` описаны `getTasks`, `getTask`, `addTask`, `updateTask` и `deleteTask`. Для списка используется тег `Task/LIST`, для отдельной задачи — `Task/id`. Создание инвалидирует список; изменение и удаление инвалидируют список и ID задачи. Активные подписки автоматически получают повторный запрос после успешной mutation.

Компоненты различают начальную загрузку, фоновое обновление, ошибку и пустой список. Для фильтрованных списков используется `currentData`, чтобы не показывать данные предыдущего набора аргументов. Тайм-аут сетевого запроса — 10 секунд. Копия задач в отдельном `tasksSlice` не создаётся.

### Избранное

`uiSlice` хранит массив строковых `favoriteUserIds` без дублей. Selectors предоставляют число избранных, сами профили и признак избранного. Одна и та же звёздочка работает в списке участников и профиле; навигационный счётчик и `/favorites` используют тот же slice.

Сохранение избранного после перезагрузки не реализовано: это дополнительная, а не обязательная часть семинара.

## 5. Обработка граничных случаев и безопасность

- **Сеть/API недоступны:** показывается понятная ошибка; пользователь может повторить запрос. Запросы пользователей и RTK Query прерываются по тайм-ауту 10 секунд, а не остаются бесконечно в `loading`.
- **Повторные действия:** middleware не запускает второй запрос участников во время первого; формы и кнопки блокируют повторное сохранение/удаление во время mutation.
- **Устаревшие ответы:** `requestId` защищает `usersSlice` от позднего ответа предыдущего запроса.
- **Плохой ответ API:** перед записью в Redux проверяется структура участников, типы полей, email и уникальность ID.
- **Пустые и некорректные данные:** неизвестный участник и задача дают отдельный 404; пустой список задач отличается от ошибки сети; пустое название не отправляется.
- **URL-фильтры:** принимаются только `todo`, `doing`, `done`; дубли и неизвестные статусы удаляются из URL без добавления лишней записи в историю.
- **Удаление:** перед необратимым удалением требуется явное подтверждение.
- **Ошибки отрисовки:** Error Boundary показывает восстановительный экран вместо полностью пустой страницы.
- **Серверные ограничения:** API разрешает только локальные origin из allowlist; JSON ограничен 16 КБ; сервер принимает только ожидаемые поля; название задачи — от 1 до 120 символов; статус проверяется по allowlist.
- **Сохранение:** JSON записывается во временный файл и затем атомарно переименовывается; временный файл создаётся с правами `0600`. Повреждённая база не затирается начальными данными — сервер прекращает запуск с диагностикой.
- **HTTP-заголовки:** API добавляет `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` и `Referrer-Policy: no-referrer`.
- **Отображение пользовательских значений:** React выводит названия как текст, не использует `dangerouslySetInnerHTML`.

Это учебный локальный API без аутентификации и авторизации. CORS — не механизм аутентификации; не выставляйте сервер в публичную сеть и не используйте его для конфиденциальных данных.

## 6. Проверка проекта

Из корня проекта:

```bash
npm run build
npm test
```

`npm test` запускает встроенные Node.js-тесты API. Они проверяют:

1. начальные данные и фильтрацию;
2. отсутствующие и повторяющиеся query-параметры;
3. разрешённый и запрещённый origin, security headers;
4. некорректный и слишком большой JSON;
5. создание, изменение, удаление и HTTP-коды;
6. пустые/слишком длинные названия, неизвестные поля, статусы и участников;
7. параллельное создание записей;
8. сохранение после перезапуска API;
9. отказ при повреждённом JSON-файле без затирания исходных данных.
